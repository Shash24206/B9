1 Application and architecture

Original source: Local reproducible academic snapshot authored for Team B9 case study. Baseline version baseline-local-2026-10-11 at B9/Part1/code/digital-wallet; evolved version evolved-local-2026-10-11 at B9/Part2/code/digital-wallet. Access date: 2026-10-11. License: MIT Academic Reference License.

Environment: Java 17; Quarkus 3.40.1; Maven 3.9+; Jackson REST serialization; JUnit 5; in-memory persistence map for inspectable pattern execution; monetary calculations strictly utilize Java BigDecimal.

Scope: Inspected modules cover account balances, fund transfers, transaction lifecycle state, repository isolation, asynchronous notification broadcasts, currency conversions, transaction limit validation, and fraud screening. Real banking settlement rails, external databases, OAuth/JWT encryption keyrings, PCI DSS tokenizers, and multi-host consensus are deliberately excluded to preserve strict academic focus.

Architecture: A client issues HTTP REST requests handled by WalletResource. CDI injects WalletService (Facade). The service orchestrates conversion selection via CurrencyStrategyFactory, invokes FraudCheckChain for screening, validates transfer and daily caps via DailyLimitDecorator, records transfers in TransferRepository, and broadcasts completion events via NotificationPublisher to EmailNotification and AuditNotification. Vendor FX contracts are adapted via VendorFxAdapter.

Request and event flow:
REST Boundary → WalletService (Facade) → Currency Strategy Factory → Fraud Check Chain → Limit Decorator → Transfer Repository.
Post-transfer event: NotificationPublisher → EmailNotification & AuditNotification.
Vendor integration: VendorFxAdapter translates VendorFxClient into ExchangeRateProvider.
Figure 1: Baseline Application Architecture (PUML source: B9/Part1/architecture/baseline-architecture.puml)

Run instructions: From B9/Part2/code/digital-wallet, execute mvn quarkus:dev to start the interactive API server, or mvn test to execute unit and REST integration tests. If JDK/Maven is unexposed in the environment, tests are recorded as not_run per assignment instructions. Python and JavaScript fixtures run from B9/Part3 and pass 4/4 assertions.

2 Part 1 Pattern discovery

Method: Systematic structural and behavioral source inspection. A pattern candidate is confirmed only when distinct participant roles and explicit call/delegation interactions are verified in the codebase. Naming conventions, package names, annotations, and unverified LLM assertions alone were rejected.

2.1 Totals at the baseline

  • Confirmed pattern types: 7 (Builder, Facade, Repository, Observer, State, Command, Value Object).
  • Confirmed pattern instances: 7 independent collaborations.
  • Concrete participant classes: 9 classes implementing variable roles.
  • Unique participant symbols: 14 distinct mapped classes, interfaces, and records.
  • Rejected and uncertain candidates: 0 candidates in baseline scope (Quarkus CDI annotations and raw Map collections were not treated as standalone patterns).

2.3 One record for each pattern instance

1. Transfer Record Construction (Builder; Creational)
Roles: Builder = Transaction.Builder; Product = Transaction. (Part1/code/.../domain/Transaction.java:6-17)
Evidence: Fluent methods accumulate fields; build() enforces complete initialization. Confirmed.

2. Wallet Transfer Application Boundary (Facade; Structural)
Roles: Facade = WalletFacade; Subsystem = WalletRepository, TransferCommand, NotificationPublisher. (Part1/code/.../application/WalletFacade.java:9-16)
Evidence: transfer() coordinates account lookup, execution, and event broadcast behind a single method call. Confirmed.

3. Wallet Persistence Boundary (Repository; Enterprise)
Roles: Repository = WalletRepository; Entity = Wallet. (Part1/code/.../repository/WalletRepository.java:7-11)
Evidence: find() and save() decouple in-memory map storage from application consumers. Confirmed.

4. Transaction Completion Notification (Observer; Behavioral)
Roles: Subject = NotificationPublisher; Observer = TransactionObserver; ConcreteObservers = EmailNotifier, AuditNotifier. (Part1/code/.../notification/NotificationPublisher.java:7-11)
Evidence: Publisher maintains list of subscribers and broadcasts onCompleted() after execution. Confirmed.

5. Transfer Lifecycle (State; Behavioral)
Roles: State = TransactionState; ConcreteStates = PendingState, CompletedState. (Part1/code/.../transaction/TransactionState.java:3)
Evidence: State encapsulates valid transitions; CompletedState prohibits further execution. Confirmed.

6. Transfer Execution (Command; Behavioral)
Roles: Command = TransferCommand; Receiver = Wallet; Invoker = WalletFacade. (Part1/code/.../transaction/TransferCommand.java:5-9)
Evidence: Encapsulates debit/credit parameters and executes business mutations on wallet receiver. Confirmed.

7. Money Amount and Currency (Value Object; Domain-Driven Design)
Roles: ValueObject = Money. (Part1/code/.../domain/Money.java:6-19)
Evidence: Immutable record enforces non-negative value and currency format; provides value equality. Confirmed.

3 Part 2 Evolution and refactoring

Figure 2: Evolved Application Architecture (PUML source: B9/Part2/diagrams/evolved-architecture.puml)

CH01 — Multi-currency support:
Change and acceptance criteria: EUR-to-EUR unchanged transfer, USD-to-EUR conversion at rate 0.92, and unsupported currency pairs fail safely without conditional branches in transfer flow.
Before and after: Diff at B9/Part2/changes/Change1/diff.patch.
Implementation and tests: Added CurrencyConversionStrategy, CurrencyStrategyFactory, and VendorFxAdapter. Unit test: DigitalWalletRulesTest.convertsOnlyTheConfiguredDemoPair().
Pattern effects: Strategy (new), Simple Factory (new), Adapter (new), CDI Injection (new), DTO (new); Builder removed; Facade evolved to WalletService.

CH02 — Transaction limits:
Change and acceptance criteria: Per-transfer limit (EUR 1,000) and daily aggregate limit (EUR 1,000). EUR 900 passes; EUR 1,001 fails; EUR 300 fails if sender already spent EUR 800.
Before and after: Diff at B9/Part2/changes/Change2/diff.patch.
Implementation and tests: Added TransactionLimitPolicy and DailyLimitDecorator. Unit test: DigitalWalletRulesTest.enforcesPerTransferAndDailyLimits().
Pattern effects: Strategy (new limit policy), Decorator (newly introduced to dynamically compose daily validation over per-transfer check).

CH03 — Fraud-detection processing:
Change and acceptance criteria: Sequential screening: deny-listed beneficiaries reject immediately; transfers ≥ EUR 6,000 trigger velocity review; EUR 200 normal transfer passes.
Before and after: Diff at B9/Part2/changes/Change3/diff.patch.
Implementation and tests: Added FraudCheckChain, DenyListCheck, and VelocityCheck. Unit test: DigitalWalletRulesTest.fraudChainStopsOnDenyListAndVelocity().
Pattern effects: Chain of Responsibility (newly introduced; terminates immediately on first failure).

6 Findings, contributions and references

Findings: The case study demonstrated how design patterns isolate variation points without degrading core transfer safety. Key limitations remain: persistence relies on an in-memory map requiring migration to relational ACID storage (PostgreSQL/Panache), and live banking integrations require distributed idempotency and PCI DSS tokenization.
Contributions: Collaborative analysis, code implementations, CSV datasets, timing measurements, and report authoring performed by Team B9 members.
