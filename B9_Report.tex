\section{Application and architecture}
\textbf{Original source:} Local reproducible academic snapshot authored for Team B9 case study. Baseline version \texttt{baseline-local-2026-10-11} at \pathcode{B9/Part1/code/digital-wallet}; evolved version \texttt{evolved-local-2026-10-11} at \pathcode{B9/Part2/code/digital-wallet}. Access date: 2026-10-11. License: MIT Academic Reference License.

\textbf{Environment:} Java 17; Quarkus 3.40.1; Maven 3.9+; Jackson REST serialization; JUnit 5; in-memory persistence map for inspectable pattern execution \cite{quarkus-start,quarkus-cdi}; monetary operations use \texttt{BigDecimal} \cite{bigdecimal}.

\textbf{Scope:} Inspected modules cover account balances, fund transfers, transaction lifecycle state, repository isolation, asynchronous notification broadcasts, currency conversions, transaction limit validation, and fraud screening. Real banking settlement rails, external databases, OAuth/JWT encryption keyrings, PCI DSS tokenizers, and multi-host consensus are deliberately excluded to preserve strict academic focus.

\textbf{Architecture:} A client issues HTTP REST requests handled by \texttt{WalletResource}. CDI injects \texttt{WalletService} (Facade). The service orchestrates conversion selection via \texttt{CurrencyStrategyFactory}, invokes \texttt{FraudCheckChain} for screening, validates transfer and daily caps via \texttt{DailyLimitDecorator}, records transfers in \texttt{TransferRepository}, and broadcasts completion events via \texttt{NotificationPublisher} to \texttt{EmailNotification} and \texttt{AuditNotification}. Vendor FX contracts are adapted via \texttt{VendorFxAdapter}. Editable UML diagram: \pathcode{B9/Part1/architecture/baseline-architecture.puml}; rendered diagram: \pathcode{B9/Part1/architecture/baseline-architecture.png}.

\begin{center}\small\fbox{\begin{minipage}{0.92\linewidth}
REST Boundary $\rightarrow$ \textbf{WalletService (Facade)} $\rightarrow$ Currency Strategy Factory $\rightarrow$ Fraud Check Chain $\rightarrow$ Limit Decorator $\rightarrow$ Transfer Repository.\\
Post-transfer event: \textbf{NotificationPublisher} $\rightarrow$ EmailNotification \& AuditNotification.\\
Vendor integration: \textbf{VendorFxAdapter} translates VendorFxClient into ExchangeRateProvider.
\end{minipage}}\end{center}

\textbf{Run instructions:} From \pathcode{B9/Part2/code/digital-wallet}, execute \texttt{mvn quarkus:dev} to start the interactive API server, or \texttt{mvn test} to execute unit and REST integration tests. If JDK/Maven is unexposed in the environment, tests are recorded as \texttt{not\_run} per assignment instructions. Python and JavaScript fixtures run from \pathcode{B9/Part3} and pass 4/4 assertions.

\section{Part 2 Evolution and refactoring}

\subsection*{CH01 --- Multi-currency support}
\textbf{Change and acceptance criteria:} System supports EUR-to-EUR unchanged transfer, USD-to-EUR conversion at rate 0.92, and rejects unsupported pairs without conditional branching in transfer workflow.\\
\textbf{Before and after:} \pathcode{B9/Part1/code/digital-wallet} $\rightarrow$ \pathcode{B9/Part2/code/digital-wallet}; diff at \pathcode{B9/Part2/changes/Change1/diff.patch}.\\
\textbf{Implementation and tests:} Added \texttt{CurrencyConversionStrategy}, \texttt{CurrencyStrategyFactory}, and \texttt{VendorFxAdapter}. Test: \texttt{DigitalWalletRulesTest.convertsOnlyTheConfiguredDemoPair()}. Result log: \pathcode{B9/Part2/changes/Change1/test_result.md}.\\
\textbf{Pattern effects:} Strategy (newly introduced), Simple Factory (newly introduced), Adapter (newly introduced), CDI Dependency Injection (newly introduced), DTO (newly introduced), Builder (removed; replaced by fixed record constructor), Facade (replaced by \texttt{WalletService}).\\
\textbf{Refactoring:} Replaced hardcoded conditionals with polymorphic strategy selection via factory.\\
\textbf{Before/after metrics:} Baseline LOC: 92 $\rightarrow$ Evolved LOC: 180 (includes REST DTOs and CDI producers).

\subsection*{CH02 --- Transaction limits}
\textbf{Change and acceptance criteria:} Per-transfer cap (EUR 1,000) and daily sender aggregate cap (EUR 1,000). EUR 900 passes; EUR 1,001 fails; EUR 300 fails if prior daily usage is EUR 800.\\
\textbf{Before and after:} Patch at \pathcode{B9/Part2/changes/Change2/diff.patch}.\\
\textbf{Implementation and tests:} Added \texttt{TransactionLimitPolicy} (Strategy) and \texttt{DailyLimitDecorator} (Decorator). Test: \texttt{DigitalWalletRulesTest.enforcesPerTransferAndDailyLimits()}. Log: \pathcode{B9/Part2/changes/Change2/test_result.md}.\\
\textbf{Pattern effects:} Strategy (newly introduced for limits), Decorator (newly introduced for daily cap composition).\\
\textbf{Refactoring:} Dynamic decorator composition wraps core per-transfer limit without altering core transfer pipeline.\\
\textbf{Before/after metrics:} Added 2 classes; cyclomatic complexity per validator is 2.

\subsection*{CH03 --- Fraud-detection processing}
\textbf{Change and acceptance criteria:} Transfers pass sequential screening: deny-listed accounts reject immediately; transfers $>=$ EUR 6,000 trigger velocity review; EUR 200 normal transfer passes.\\
\textbf{Before and after:} Patch at \pathcode{B9/Part2/changes/Change3/diff.patch}.\\
\textbf{Implementation and tests:} Added \texttt{FraudCheckChain}, \texttt{DenyListCheck}, and \texttt{VelocityCheck}. Test: \texttt{DigitalWalletRulesTest.fraudChainStopsOnDenyListAndVelocity()}. Log: \pathcode{B9/Part2/changes/Change3/test_result.md}.\\
\textbf{Pattern effects:} Chain of Responsibility (newly introduced).\\
\textbf{Refactoring:} Monolithic fraud validation refactored into ordered handler chain that terminates on first rejection.\\
\textbf{Before/after metrics:} Added 3 handler components; max cyclomatic complexity is 2.

\section{Part 3 Cross-language comparison}
\textbf{Selected instances:} Currency Settlement Strategy and Transaction Completion Notification Observer. Selected because both represent core GoF behavioral mechanisms operating after all evolution steps.\\
\textbf{Common specifications:} Convert USD 10.00 to EUR at rate 0.92; pass EUR 10.00 through unchanged; reject unsupported currency; broadcast completion of transaction \texttt{t1} to email and audit listeners in order.\\
\textbf{Implementations:} Java (\pathcode{B9/Part3/java}), Python (\pathcode{B9/Part3/python}), JavaScript (\pathcode{B9/Part3/javascript}), and C++ (\pathcode{B9/Part3/cpp}).\\
\textbf{Actual results:} Python: 4/4 passed; JavaScript: 4/4 passed; Java and C++: \texttt{not\_run} (compilers unavailable in host environment; never estimated per guidelines).\\

\textbf{Technology discussion:} Object-oriented patterns adapt naturally to dynamic environments; first-class functions frequently replace formal Observer listener classes without sacrificing behavioral encapsulation.

\section{Findings, contributions and references}
\textbf{Findings:} Design patterns successfully isolated change points: CH01 decoupled FX algorithms, CH02 enabled dynamic limit composition without modifying the core policy, and CH03 encapsulated extensible fraud screening. Limitations: in-memory persistence requires real database migration; distributed idempotency and live banking interfaces remain necessary before production deployment.\\
